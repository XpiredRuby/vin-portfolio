01Problem

Flight software is judged on evidence, not on features. The question at any review is not "does it work" but "show me the run where it did not, and show me what it did about it." Producing that evidence normally requires a lab: a flight-like target, a ground station, a way to corrupt the link on purpose, and an automated way to repeat the whole thing after every change.

A student cannot get access to that lab. AstraSim-FSW was built to answer the question of whether the entire verification chain — flight target, ground segment, fault injection, regression, evidence capture — could be constructed from a Raspberry Pi and a laptop, and still produce artefacts that would survive being shown to a flight software engineer.

Problem statement. Build a flight software core and a verification campaign around it, on commodity hardware, that produces reproducible, machine-readable evidence of correct behaviour under both nominal and fault conditions.

Engineering
  • No reliable transport. UDP was chosen deliberately — if the software assumes delivery, the fault handling is untested fiction.
  • Evidence is a deliverable. A run that does not leave artefacts did not happen.
  • Same tests, both architectures. A suite that only passes on the development host proves nothing about the target.
  • Determinism. Every stochastic behaviour is seeded so failures are reproducible.

04System design

Two segments with a deliberately hostile link between them. The ground segment issues commands, decodes telemetry, and — critically — contains a fault injector that can drop, corrupt and delay packets on demand. The flight segment parses, validates, acts, and reports, and is responsible for behaving correctly when the link misbehaves.

Design decisions

05Interface & protocol

The interface control definition is the contract between segments. It is fixed-width, little-endian, and validated before a single field is trusted.

— packet layout — 0 1 2 3 4 N-2 N ┌────────┬────────┬────────┬────────┬─────────────────┬────────────┐ │ SYNC │ TYPE │ SEQ │ LEN │ PAYLOAD │ CRC-16 │ └────────┴────────┴────────┴────────┴─────────────────┴────────────┘ — validation order, strictest first — 1. SYNC word matches → else discard, do not advance state 2. LEN within bounds → else discard (guards the payload read) 3. CRC-16-CCITT over [TYPE..PAYLOAD] matches trailer 4. TYPE is a known command 5. SEQ is not a replay → only then: dispatch to the command handler

The ordering matters. Length is validated before the payload is read, so a corrupted length field can never cause an over-read — the check that protects the parser cannot depend on data the parser has not yet verified.

06Algorithms & logic

  • CRC-16-CCITT, table driven. A 256-entry lookup table replaces per-bit computation.
  • Mode state machine. Safe / nominal / fault with explicitly enumerated legal transitions; illegal transitions are a test assertion, not a comment.
  • Watchdog. A missed-tick counter that triggers an autonomous transition to safe when ground contact is lost, independent of any command.
  • Health monitor. Limit checking plus trend detection, so a parameter walking toward a limit is caught before it crosses it.
  • FDIR response. Detection, isolation and a defined recovery action per fault class, with the transition recorded in telemetry so the ground can see why the vehicle changed mode.
  • Seeded Monte Carlo regression. 25 trials with dispersed fault timing and packet loss, all reproducible from their seeds.

What is real vs. what is replayed

The C++ target was built on Raspberry Pi aarch64, accepted UDP commands, produced telemetry, passed 9/9 tests and generated committed evidence files. The live demo workstation deterministically replays that recorded run so the verification sequence can be reviewed without coordinating terminals — it visualises real evidence, it does not simulate results.

08Testing

  1. Unit tests. CRC computation against known vectors, packet encode/decode round-trip, state-machine transitions including every illegal transition.
  2. Nominal scenarios. YAML-defined command sequences with expected telemetry responses and acknowledgement matching.
  3. Fault injection. Dropped packets, bit-flipped payloads, corrupted length fields, delayed delivery, and total link loss — each with an asserted expected response.
  4. Monte Carlo regression. 25 seeded trials dispersing fault timing and loss rate, run as a gate on changes.
  5. Hardware target execution. The same suite re-run on aarch64, because endianness, alignment and timing behaviour differ from the host.

09Validation

Verification asks whether the software meets its requirements. Validation asks whether meeting them actually produces safe behaviour. The distinction shows up clearly in the watchdog: it is straightforward to verify that a missed-tick counter fires, and much more interesting to validate that the resulting safe-mode transition happens fast enough to matter, and that it does not fire spuriously under normal packet loss.

  • Requirement traceability. Each requirement maps to at least one executing test, and the mapping is checked rather than asserted.
  • Negative testing. Every integrity mechanism is validated by breaking it on purpose — a CRC check nobody has ever seen reject a packet is an untested branch.
  • Cross-architecture evidence. Passing on the host and on aarch64 validates that no host-specific assumption about width or alignment leaked into the packet layer.

10Performance

The first CRC implementation computed bit-by-bit and produced measurable packet-validation latency on the Pi — visible as jitter in the telemetry cadence, which is exactly the sort of thing that is invisible on a development laptop. Migrating to a table-driven CRC-16-CCITT implementation reduced packet validation overhead by 40% and flattened the telemetry timing.

11Results

  • Full command and telemetry chain operating on a hardware target, with committed evidence files rather than screenshots.
  • 9/9 CTest suites, 5/5 YAML scenarios and 25/25 Monte Carlo regressions passing on both host and Raspberry Pi.
  • Every injected fault class — drop, corruption, delay, link loss — produced the designed response, including autonomous safe-mode entry on watchdog expiry.
  • A 40% reduction in packet validation overhead from the table-driven CRC migration, verified on the target rather than inferred.
  • A replayable evidence workstation that lets a reviewer inspect the verification sequence in a browser.

13Lessons learned

  • Profile on the target, not the host. The CRC cost was invisible on a laptop and obvious on the Pi. Development-host performance is not evidence.
  • Validate before you parse. Ordering the checks so that length is verified before the payload is read is the difference between a robust parser and a buffer overrun.
  • Test-only code in a flight build is a liability. Keeping the fault injector on the ground side keeps the flight binary honest.
  • Evidence is the deliverable. The artefacts — logs, plots, test output — are what let someone else believe the claims without re-running anything.
  • A protocol is a contract. Writing the ICD before the code eliminated an entire class of integration argument.

14Future work

  1. Live WebSocket telemetry bridge so the workstation shows a running target rather than a replay.
  2. Real-time clock integration and a hard timing budget with measured worst-case execution time per task.
  3. Physical sensor in the loop, closing the last gap between software-in-the-loop and true hardware-in-the-loop.
  4. Requirement coverage reporting generated automatically from the test run rather than maintained by hand.
  5. Expand the FDIR matrix to cover sensor faults, not only link faults.
